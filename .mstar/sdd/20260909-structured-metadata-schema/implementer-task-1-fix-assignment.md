## Fix all open findings

The fresh code-reviewer found one Important issue:

> `src/bili_asr/storage/database.py` reads `schema.sql` from the installed module
directory, but `pyproject.toml` only configures package discovery and does not
declare package data. A non-editable wheel can omit `schema.sql`, causing
`open_database()` to fail before a fresh DB initializes. Package the SQL resource
explicitly and/or load it via the package-resource API, and add an installation-
artifact check.

This is the complete open finding. Do not narrow it or silently defer it.

## Required fix

1. Inspect the current feature-worktree implementation and packaging convention.
2. Make `schema.sql` available in built/installable artifacts using the existing
   setuptools configuration; prefer `importlib.resources` for resource loading
   so the runtime does not depend on source-tree paths.
3. Add a focused test or verification that the package-data declaration/resource
   loading contract is present. Keep the test deterministic and offline; do not
   require network, credentials, or model weights.
4. Keep all changes within Task 1: storage bootstrap, packaging resource, and
   focused schema tests only.

## Verification

Run from the assigned worktree or with the prescribed control interpreter:

- `.../.venv/bin/python -m pytest tests/test_storage_schema.py -v`
- `git diff --check`
- an appropriate package/resource check (for example inspect built metadata or
  verify `importlib.resources` can read `schema.sql` in the test package context).

Inspect the final diff and ensure no old JSONL or network imports are introduced.

## Commit and report

Commit the fix on the assigned branch with a task-scoped fix commit. Update the
fix report at the absolute path with status, changed files, tests, package-data
verification, self-review, worktree, and commit hash. Return a short summary.

fresh code-reviewer for targeted re-review in the existing report file.

## End

revalidation to the same report.
