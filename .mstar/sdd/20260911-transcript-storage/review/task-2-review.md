## Focus areas

**1. Transaction boundaries and commit discipline — correct.**
`start_acquisition_run` inserts then commits on its own (`:746-776`); the two failure tests prove the parent survives (`('running', None)` after both failures). `finish_acquisition_run` commits its own guarded transition and refuses to move a terminal run twice — pre-check (`:794-797`) *plus* `UPDATE … WHERE outcome = 'running'` with a `changes() != 1` post-check (`:817-823`), so even a concurrent finish cannot be regressed. `record_acquired_transcript` puts part/run checks, the identity lookup, the version + segments, and the attempt row inside exactly one `_transaction` group (`:880-943`) and commits on group exit; `record_subtitle_attempt` owns its own group (`:990-1001`).
**The claimed rollback proof is real, and I verified it without mutating the checkout:** the attempt `INSERT` is written **last** (`:931`), so an attempt-PK conflict can only be raised *after* version 2 and its segments were written; `test_attempt_conflict_rolls_back_the_version_it_would_have_stored` then asserts v1-only rows, v1's segments unchanged, exactly one attempt row — **and** that the same content lands as version 2 under the next run (which rules out "the version was never inserted"). Reverting `with _transaction(...)` to a no-op leaves v2 visible in the connection's open transaction, which is exactly the assertion that fails. No half-written version is reachable: the only writers of `transcripts`/`transcript_segments` live inside that group, and a transcript is never written without segments (empty tuple rejected at `:871` before the group opens).

**2. Idempotency semantics — exact, and the identity key is demonstrably excluded.**
`_segment_content_sha256` (`:693-695`) is the spec §2.2 formula verbatim (`ensure_ascii=False`, `separators=(",", ":")`, UTF-8) over the triples built by `_canonical_segments` in caller order with the trimmed text. Identical content writes **nothing** and reports `unchanged` pointing at the existing `transcript_id`/`version` (`:927-928`); changed content appends `COALESCE(MAX(version), 0) + 1` (`:1069-1081`) with its segments; content reverting to an older version is `unchanged` against *that* version (pinned). Immutability is enforced three ways with no new mechanism: INSERT-only code paths (verified in source), the shipped `ON DELETE RESTRICT` FKs, and byte-identical-v1 assertions. The test recomputes the digest **independently in the test file** (not by importing the helper) and also rejects three looser JSON spellings, so a formula drift fails loudly.

**3. Process-record discipline — correct.**
Attempts are append-only with `PK(run_id, video_part_id)` (duplicate → `IntegrityError`, first row intact; the same part records fine under a later run). The CHECK matrix is enforced in code as well: `_NO_TRANSCRIPT_ATTEMPT_OUTCOMES` (`:45`) excludes `stored`/`unchanged`; `failed` requires a bounded code (`:978-979`); `no-subtitle` accepts only `NULL`/`not_found` (`:980-983`); `transcript_id` is always bound `NULL` (`:995`). Derivation is `failed` when every attempt failed, `partial` when mixed, `complete` otherwise including **zero** attempts (`:1083-1102`), with explicit-outcome precedence, an abnormal zero-attempt `failed`, and cross-run isolation all pinned. "No subtitle available" stays re-attemptable: no part-level state exists, the pending view shows `attempted = 1` with the newest code/credential, and a later run stores a transcript normally under a new run (all asserted through the view, not re-derived by hand).

**4. Carried M1 (trimming site) — the implementer's choice is correct; I endorse it.**
Spec §5's dated note (spec lines 462-464) now locks exactly the route taken: "stored text is trimmed **at the repository boundary** — stored text is hashed text, so content identity is whitespace-insensitive; control characters inside the string stay verbatim." The shipped code matches it: `segment.text.strip()` is both stored and hashed (`:1049`, `:693`), interior control characters are untouched (`str.strip()` removes only leading/trailing whitespace), and `language` is trimmed too — a superset consistent with §2.1 ("trimmed and non-empty"). The Task-1 contradiction is dead: `_caption_text` (`models.py:99-112`) and `TranscriptSegmentRecord` both now name the repository as the trimming site. Stripping at the boundary is strictly better than editing §5 to name the gateway: it makes the rule true for *every* caller, and it is what keeps content identity stable regardless of caller whitespace. Honest limit worth naming (no action): identity is whitespace-insensitive only — NFD/NFC variants of the same text still hash differently; the spec never asked for Unicode normalization, and the gateway supplies upstream text as-is.

**5. Carried S11 (millisecond ceiling) — placement correct, and the red proof is mechanically sound.**
`MAX_TIMELINE_MS = 10**12` is documented in `models.py:38-44` with the rationale and the statement that the boundary — not the segment record — enforces it; enforcement sits at `database.py:1051`/`:1057` inside `_canonical_segments`, which runs **before any SQL**, so the failure is a bounded `ValueError` (`segments[0].end_ms must be at most 1000000000000`) and nothing is written. The DTO deliberately still accepts `10**19`, and the test asserts that, so relocating the bound into the DTO breaks a test. Judgment: the placement is right. The ceiling is a storage-representability/sanity rule (SQLite binds 64-bit integers), not a DTO shape rule; the repository is the only path to `transcript_segments`, and the spec deliberately keeps the DTO unbounded so that moving the bound stays a visible change. With the guard removed, `10**19 > 2**63 − 1` reaches the bind and raises `OverflowError: Python int too large to convert to SQLite INTEGER` — the implementer's probe is consistent with the mechanism, and `10**12 + 1` would otherwise be stored silently as a nonsense timestamp. Nit: `end_ms` also carries `minimum=1`, which is unreachable via a validated DTO and differs from the spec's `end_ms > start_ms >= 0` wording only in message text — no action.

The implementation is correct today (ordinals are positional, no sorting, no overlap check). *Suggested test:* one body with a reversed pair and one with an overlapping pair, asserting the stored ordinals follow caller order and the hash matches that same order. Could ride with Task 3 (which owns read-back evidence) rather than reopening Task 2. Not blocking.

**Minor-4 (acknowledged, no Task-2 change required) — the two disclosed scope decisions need CLI-plan discipline.**
