#### 🔴 The AAC fallback cannot decode AAC under the `librosa` the project declares and resolves

- **Evidence**: `bilibili-asr-archive/src/bili_asr/asr.py:403-406` — `except sf.LibsndfileError: import librosa; librosa.load(...)`; `bilibili-asr-archive/pyproject.toml:36` declares `librosa>=0.10` (no upper bound); `bilibili-asr-archive/README.md:143-144` asserts `audioread` is a hard dependency of `librosa`.
- **Impact**: on a fresh install the fallback re-raises the very error it exists to catch, so the `.m4a` path stays broken **and every gate stays green**. Measured on the target host, same source, same AAC file: under `librosa 1.0.0` (a clean `.[asr]` resolution) `asr._read_audio` raises `soundfile.LibsndfileError`; under `0.11.0` (the host's venv) it returns `(89088,) rate 44100`. librosa 1.0.0's core deps no longer include `audioread`, its `core/audio.py` has zero `audioread` mentions, and its `load()` is a bare `__soundfile_load` call.
- **Merge class**: must-fix
- **Confidence**: HIGH
- **Fix sketch**: bound the extra (`librosa>=0.10,<1`) and refresh `uv.lock`, or decode non-libsndfile containers through an explicit backend (`audioread` directly, or the `ffmpeg` the README already names as the real dependency).

<sub>Scoped honestly: the host where T5 ran is `librosa 0.11.0`, where the fallback works. The defect is in the dependency contract the repo publishes, not in that machine's behaviour — but that contract is what a rebuilt host gets.</sub>
