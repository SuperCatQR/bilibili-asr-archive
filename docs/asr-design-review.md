# 面向归档与阅读的 ASR 设计建议

日期：2026-10-08。代码核对基准：`cb23383`。

本文是设计评审与实施建议，不包含真实 GPU 基准结果。第 3 节描述评审基准的缺口；独立分支已推进第一批配置快照、离线加载、模型版本拆分和运行诊断，已实现行为、使用方法与边界见 [ASR 参数与诊断](asr-configuration.md)。其余建议仍待实施；推荐参数需用项目音频验证。

同日后续已完成 [公开中文样本实测](asr-public-samples.md)：12 条 FLEURS 音频的 Chinese / auto 输出一致，严格 CER 均为 7.38%；138.6 秒人工拼接音频在 180 / 120 秒下为 7.12%，60 秒下为 7.89%。8 秒纯静音在三个设置下均生成“嗯。”，所有短样本均触发跨度告警，包括 5 条 CER 为零的样本。因此下一步优先增加静音与语音条件诊断、校准覆盖告警，保持现有分块默认值，继续用真实项目音频验证。以上是 CPU 单轮结果，不构成 GPU 性能结论。

## 1. 项目定位与设计取舍

[README](../README.md) 将项目定义为本地视频转录归档流水线：SQLite 保存元数据、转录版本、任务、尝试和发布记录，音频与文本文件是可校验的产物。[校对架构](ai-proofreading-architecture.md) 进一步区分原始证据、AI 阅读修订和人工版本。字幕采集与 ASR 是独立来源，校对使用固定的基础转录和可选参考。

据此，ASR 应提供完整、时间可回查、来源可追溯的基础转录。整理口语、组织阅读段落和修订疑点属于后续 editorial 流程。设计优先级建议为：

1. 保全音频与识别证据，显示漏识别、截断和不确定性。
2. 冻结输入与有效配置，使结果可解释、实验可复核。
3. 支持长任务恢复，避免 GPU 卡住导致工作流失去进展。
4. 在上述约束内改善准确率、时间戳和批量吞吐。

这是由项目定位推导的优先级，并非模型文档给出的通用排序。

## 2. 资料与适用范围

| 官方资料 | 可确认的能力或约束 | 对本项目的用途 |
|---|---|---|
| [Transformers：Qwen3 ASR](https://huggingface.co/docs/transformers/model_doc/qwen3_asr) | 原生 `-hf` checkpoint、识别与强制对齐接口、语言和上下文 prompt | 保留当前模型接口；把生成与对齐配置显式记录 |
| [Qwen3-ASR 官方仓库](https://github.com/QwenLM/Qwen3-ASR) | 0.6B / 1.7B ASR、BF16 示例、批量推理、对齐器的语言与时长范围 | 以当前 1.7B 为基线，按设备测量；限制对齐输入长度 |
| [Transformers：KV cache](https://huggingface.co/docs/transformers/kv_cache) | KV cache 减少生成中的重复计算；不同缓存策略有显存和速度取舍 | 验证二遍识别关闭 cache 的成本；缓存实验单独留证据 |
| [Silero VAD](https://github.com/snakers4/silero-vad) | 支持 8 kHz / 16 kHz，返回语音区间时间戳 | 为漏识别检测提供辅助语音区间，不直接裁掉原始音频 |
| [JiWER](https://jitsi.github.io/jiwer/) | CER、WER 和空参考样本的错误计数 | 中文人工基准以 CER 为主；静音幻觉单列统计 |
| [PyTorch：可复现性](https://docs.pytorch.org/docs/stable/notes/randomness.html) | 跨版本、平台、CPU / GPU 不保证完全相同；确定性算法存在性能与支持限制 | 保存运行环境；基准模式可选择确定性，避免承诺跨机器逐字节一致 |
| [SQLite：事务](https://www.sqlite.org/lang_transaction.html) | 可并发读，同一数据库只能有一个并发写事务 | 模型在事务外执行，领取、检查点与最终写回使用短事务 |

检索日期均为 2026-10-08。示例中的 batch size、token 上限和加速数据属于对应环境的例子，不能直接作为 RX 7800 XT / ROCm 的最优参数。

## 3. 当前实现与确认的缺口

| 源码位置 | 当前行为 | 设计缺口 |
|---|---|---|
| [ASR 配置](../src/bili_asr/asr/config.py) | 定义分块、超时、热词、离线标志等；提供环境配置解析 | 分块长度没有有限值检查；离线标志没有在模型加载处强制落实 |
| [ASR profile](../src/bili_asr/storage/workflow.py) | profile digest 包含模型、单个 revision、aligner、设备与语言 | 未冻结分块、热词、生成策略等影响输出的参数 |
| [workflow handler](../src/bili_asr/workflow_runtime.py) | 从 profile 直接构造配置；GPU 使用可终止子进程，CPU 缓存 runner | 分块、热词与超时的环境配置没有进入主工作流；GPU 每个任务重新加载模型 |
| [runner](../src/bili_asr/asr/runner.py) | BF16 加载两套模型，逐块识别并对齐；有条件执行整份音频的第二遍 | 第二遍关闭 KV cache；缺少分阶段耗时和逐块截断状态；ASR 与 aligner 共用 revision |
| [分块](../src/bili_asr/asr/audio.py) | 180 秒附近寻找低能量边界，无重叠、无缺口地覆盖输入 | 无持久化分块计划与块级恢复 |
| [覆盖率](../src/bili_asr/asr/coverage.py) | 首尾字幕跨度除以解码时长 | 中间漏识别可能仍显示 100%；长静音也可能造成误报 |

前次审查的小例子已确认：环境设为 60 秒分块、600 秒超时，主工作流构造方式仍得到 180 秒、1800 秒。600 秒音频只在首尾各产生 10 秒字幕，当前跨度覆盖率仍为 1.0。以上是代码行为验证，不是模型准确率测评。

## 4. 建议的数据与执行边界

继续由现有 SQLite workflow 管理任务、租约与重试。ASR 模块处理媒体和模型，不直接承担发布与阅读稿整理。建议一次运行按下面的顺序执行：

1. 绑定成功 audio prerequisite 的音频身份、不可变 profile 和固定参考版本。
2. 解码、重采样并生成覆盖全部输入的确定分块计划。
3. 逐块识别，保存原始文字、语言、生成状态和耗时。
4. 默认保持空热词；既有显式热词配置仍按冻结的策略执行。
5. 对最终文字进行强制对齐，汇总时间戳与质量证据。
6. 在短事务中追加原始 transcript version；独立规划发布和可选校对。

建议把识别与对齐拆成模块内的两个阶段，第二遍仅重做必要的识别，最终文字对齐一次。外部继续保留一个 ASR job；最初无需把每个块扩展成新的 workflow job 类型。

### 4.1 冻结有效配置与运行环境

影响输出的配置应进入版本化 profile；运行时不得悄悄从新环境变量覆盖已规划任务。新增配置需要显式的 profile 格式版本和数据库迁移方案。

| 类别 | 建议记录的字段 |
|---|---|
| 模型身份 | ASR 与 aligner 各自的逻辑 ID、revision；本地模型的内容清单摘要或可验证的下载 snapshot 身份 |
| 音频处理 | sample rate、声道策略、分块算法版本、目标秒数、边界搜索范围 |
| 解码策略 | 语言、有效 prompt / 热词、生成上限公式、采样参数、cache 策略 |
| 对齐策略 | aligner 语言、输入长度限制、时间戳与字幕整形策略版本 |
| 运行控制 | 超时、重试预算、worker 生命周期；单独保存，不必全部参与内容配置摘要 |
| 运行事实 | torch、transformers、GPU runtime 版本、设备、dtype、实际加载身份、阶段耗时 |

两个模型的 revision 分别固定。一个仓库的 commit SHA 不应被当成另一个仓库的 revision。冻结配置提供可追溯性；跨硬件完全一致仍受 PyTorch 限制。

`offline` 若作为产品承诺，应在模型与 processor 加载处统一落实，例如 `local_files_only=True`，并验证缺少本地权重时给出明确错误。配置和运行记录应继续沿用项目的凭据与本地路径脱敏规则。

### 4.2 保全分块输入，增加恢复能力

保留完整解码音频及原始时间轴。低能量分块先作为基线；VAD 初期只用于分析。由 VAD 直接删除片段，可能丢掉轻声、音乐中的语音和错误判定的语音。

建议持久化分块计划和检查点：`chunk_index`、样本起止位置、分块计划摘要、配置摘要、识别文字、对齐结果、阶段状态与质量标记。检查点必须绑定音频身份和配置，恢复前验证一致性。

检查点写入同样校验当前 lease owner 和 attempt。过期 worker 不得提交权威检查点；是否复用前一次 attempt 的已完成块，应由当前 attempt 校验后决定。最终 transcript 只包含经过汇总验证的结果。

第一阶段保留无重叠分块。只有基准证明边界漏字明显，再实验小范围重叠；届时必须设计重叠文字与时间戳去重，并记录算法版本。

### 4.3 质量证据与工作流状态分别表达

`job succeeded` 表示执行完成，不等于全文准确。建议质量结果同时记录可评估性和具体原因：输入无法评估、未发现已知风险、需要复核。未经人工听校不能宣称内容已经准确。

| 证据 | 能发现的问题 | 不能证明的事情 |
|---|---|---|
| 解码时长与完整分块计划 | 输入解码不足、块缺失、范围不连续 | 模型识别准确 |
| 每块空输出与异常状态 | 有输入却没有文字、局部失败 | 空输出一定是漏识别 |
| 生成上限、EOS、重复特征 | 可能截断或异常重复 | 达到上限必然截断；正常结束必然完整 |
| 语音区间与原始对齐单元的匹配 | 疑似未覆盖语音、长时间缺口 | 对齐文字正确、VAD 没有漏检 |
| 时间戳检查 | 负值、倒序、超出对应音频块等 | 每个时间戳在听感上准确 |
| 人工参考 CER 与重点词审核 | 内容错误、专名和数字偏差 | 未抽样内容同样准确 |

当前跨度覆盖率应保留为明确命名的历史指标，便于兼容旧记录。新增语音区间覆盖率时，记录 VAD 版本、参数、区间与容差；分母没有有效语音时标为不可评估。使用原始对齐单元而非整形后字幕大段跨度，减少字幕合并跨过静音造成的偏差。

VAD 区间覆盖仍是辅助信号。语音被识别为错误文字也可能具有完整对齐；CER 和人工复核提供另一层证据。

### 4.4 热词与阅读校对

项目策略为热词一般不考虑，默认保持为空，不列入常规调优计划。该取舍基于用户对大样本场景下副作用的顾虑；公开样本测试未验证热词的收益或副作用。已有热词能力与历史配置继续保留，显式使用时参考字幕版本、有效热词和最终 prompt 仍应冻结。

默认空热词不会触发热词第二遍，因此第二遍 cache 不属于当前常规性能调优重点。当前没有显式把第一遍的 `past_key_values` 传给第二遍，仅凭现有注释不能确认关闭缓存是必要条件。

现有显式热词配置仍受“第一遍出现才准入”的证据策略约束；本轮不推进领域词表或热词纠错扩展。

ASR 原文保持独立。AI 校对修改口语表达时，仍通过 editorial revision 与 review 文档追溯；不得用更流畅的阅读稿充当 ASR 的人工标准答案。

### 4.5 GPU 生命周期与超时

先记录模型加载、音频处理、解码、对齐、写回和总耗时。仅在加载成本占比显著时，引入由父进程监督的常驻 GPU 子进程，正常复用模型，超时或异常时杀掉并重建。

建议每块上报阶段进展，父进程区分总预算与无进展超时。总预算可依据音频长度、对应设备的实测 RTF、冷启动成本和安全余量估算，并设置显式上限；不能只用模型输出 token 的心跳判定 GPU 健康。

单 GPU 先限制为一个活动推理 worker，避免重复加载模型竞争显存。需要批量或编译优化时，再比较真实 ROCm 数据。官方其他设备上的加速数据仅作实验线索。

对齐语言必须核对所用 aligner 的支持范围。超出支持范围或没有可靠语言证据时，应显式报告时间戳不可用或需要复核，避免默认强行按中文对齐而产生可信外观的错误时间戳。

## 5. 参数实验与验收

**当前证据支持继续使用**现有模型组合、BF16、16 kHz、中文任务显式 Chinese、180 秒分块及现有生成预算。热词默认空，不纳入常规调优。公开构造样本未证明缩短分块改善准确率；真实项目长视频可优先对照 120 / 180 秒，尚无证据证明其中哪个最优。分块搜索可能超过目标秒数，实际输入长度必须受 aligner 上限约束。

| 顺序 | 实验 | 决策依据 |
|---|---|---|
| 1 | 修正配置入口与质量记录 | profile 差异实际传到模型；中间漏块被标记；历史指标语义保持清楚 |
| 2 | 60 / 120 / 180 秒分块 | CER、边界漏字和重复、异常空块、RTF、峰值显存 |
| 3 | 自动语言与显式 Chinese | 纯中文与中英混合样本分别评估 |
| 4 | 解码与对齐阶段性能 | 输出一致性、各阶段耗时；默认空热词不触发第二遍 |
| 5 | 当前 token 预算与截断恢复 | 上限触发率、EOS、重复；可疑块缩短重识别后的内容变化 |
| 6 | 常驻 GPU worker、批量与编译 | 冷启动占比、稳定性、OOM、超时恢复、长期资源占用 |
| 7 | 1.7B 与 0.6B | 准确率和重点词损失是否值得资源节省 |

基准集应固定音频哈希、人工转写、规范化规则和样本选择理由，覆盖长讲座、短视频、专名术语、中英混合、音乐、静音、轻声及分块边界。先选择固定的小样本完成探索，再用未参与调参的保留样本确认。

中文以 CER 为主要文本指标，并分别记录专名、数字、否定和语义关键项的人工审核结果。标点、空格和数字归一化规则必须版本化；同时保留严格文本比较，避免归一化隐藏数字或专名错误。

静音样本单独报告非空输出比例与插入字符数。JiWER 空参考的错误计数不能按普通百分比理解，也不应不加说明地与语音样本平均。

性能同时报告冷启动与模型复用条件下的 RTF（处理秒数 / 音频秒数）、阶段耗时、峰值显存和失败次数。字幕来源仅作辅助参考；人工回听提供基准证据。已润色的阅读稿不能作为识别正确率参考。

验收至少包含：

- 配置冻结：环境改变不影响已有任务；相同有效输入与配置可解释地复用，新配置产生新 profile / run；相同文本可复用既有 transcript version。
- 完整性：中间空块、截断、局部失败与正常静音都有可区分的记录。
- 恢复：超时、进程退出和 lease 丢失后可重新领取；旧 worker 无法写回新 attempt。
- 数据保全：新识别与校对不覆盖原始来源；发布可以追溯到准确的 transcript version。
- 性能：有真实模型数据支持优化结论；模型替身测试只验证控制流程。

## 6. 建议实施批次

**第一批：建立可信的测量基础。** 扩展版本化 profile 与迁移，分开两套模型 revision，落实离线行为，校验有限值，增加阶段耗时、逐块状态与生成风险记录。新增中间漏识别反例的测试，并修复与当前架构不一致的历史测试引用。

**第二批：用固定音频调参。** 比较分块与语言，分析解码和对齐阶段性能，引入可选 VAD 质量分析。默认空热词，热词与其第二遍不列入常规调优。依据结果决定参数，不自动把全部任务改成两遍或更短分块。

**第三批：提高批量执行效率。** 增加分块检查点与恢复，评估受监督的常驻 GPU worker。确认瓶颈后再引入批量、编译或其他推理后端。

每批均保持 SQLite 为任务与版本的事实源，使用事务外推理和短事务写回。原始归档发布与阅读校对继续独立推进。
