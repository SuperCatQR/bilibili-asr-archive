# Design philosophy — B 站视频归档整合工作流

Status: **项目北极星**（2026-10-03 定稿于分支 `thinking`；2026-10-04 修订，已在 `main`）。
本文是产品方向的上游锚点：新环节、新数据源、新处理器的设计先对齐这里，再谈实现。
实现约定的词汇表在仓库根的 [`CONCEPTS.md`](../../CONCEPTS.md)；本文不重复定义，只陈述方向与公理。

---

## 1. 定位

项目不再只是"ASR 转录归档工具"。它是一个 **B 站视频的归档整合处理工作流**：

> 把 B 站视频抓下来整理为数据库，对视频内容进行归档与多维度加工。
> 当前着眼点是音频；画面、评论、视频间关系是已确认的拓展方向。

工作流由**三大环节**组成，环节之间是严格的单向数据流：

```
┌──────────┐   facts    ┌──────────┐  artifacts  ┌──────────┐
│ 视频抓取  │ ────────→  │ 内容处理  │ ────────→  │ 数据处理  │
│(acquire) │            │(process) │            │ (derive) │
└──────────┘            └──────────┘            └──────────┘
 唯一可变边界             纯派生                  派生之上再派生
```

- **视频抓取**：系统与外部世界之间唯一的状态可变边界。
- **内容处理**：把字节本体（当前是音频）变成 artifact 的处理器集合；ASR 只是其中一个实例。
- **数据处理**：在已有 artifact 之上做收集 → 处理 → 输出的派生（当前未系统性展开，见 §4）。

### 1.1 环节的职责边界

| 环节 | 职责 | 绝不做什么 |
|---|---|---|
| 抓取 | 把外部世界某时刻的观察忠实、带时间戳、可重放地固化 | 不做理解、不做质量判断、不做内容变换 |
| 内容处理 | 对不可变字节应用处理器 `f`，产出带血缘的 artifact | 不碰网络、不改写输入 |
| 数据处理 | 在 artifact 图上做派生、求值、收敛 | 不引入未固化的新外部数据 |

## 2. 抓取是唯一可变边界

B 站是不可信的外部世界：视频会消失、字幕会变、评论会增长、账号会被风控。
因此抓取环节的输出被定义为**事实（facts）**：一次观察就是一条不可变记录，带着观察时间戳。

这条边界一旦守住，就获得本项目最重要的自由度：

> **除抓取外，任何环节出错、改算法、换模型，都可以安全地从头重跑，
> 而不需要再向 B 站请求一次。**

重放能力 = 可演进能力。这正是"数据可能极度庞大"焦虑的正解：
规模带来的最大风险不是存不下，而是"旧数据是用旧逻辑产的，逻辑改了数据没法升级"。
有重放，升级就是重算。

### 2.1 渐进式固化

已有的分层爬取是这一原则的体现，要保持并推广：

1. `ingestion_discoveries`：枚举时先固化"发现了什么"（轻量、便宜、可大批量）。
2. `video_details`：按需固化详情。
3. `audio_objects`：最后固化字节本体（最贵、最 selective）。

未来的评论、画面帧沿用同样的渐进分层：先观察存在性，再按需固化内容。

## 3. 内容处理：处理器注册表

公理：

> **内容处理 = 任意函数 `f: (immutable bytes) → artifact`。ASR 只是 `f` 的一个实例。**

- ASR：audio → 文本（已有）
- 响度 / 频谱 / 时长统计：audio → 数值（便宜，先行）
- 声纹 embedding、音乐/语音分类、说话人分段、BPM：audio → 向量/标签（候选）
- 抽帧、场景切分、画面 OCR：video → 帧/文本（画面方向，见 §6）

架构形态：**一个处理器注册表 + 一个缺口队列**。
处理器声明自己的输入类型与输出版本（`name@version`）；
系统对 `(输入, processor@version, params)` 求差集得到"还没跑过的组合"并调度。
输入不可变，所以任何处理器可以随时对全库安全重算。

这一层同时天然回答了数据处理 loop 里"收集数据"的实现：
**收集 = 声明依赖 + 求缺口**，而不是手写查询代码。

## 4. 数据处理：loop 收敛成派生图

设想中的基本 loop 是"收集 → 处理 → 输出，循环 n 次直到符合预期"。
关键的设计修正是：

> **loop 不该实现成一个带循环和状态变量的命令式过程，
> 而该展开成一条有向无环的派生链。**

```
fact ──→ f1 ──→ artifact1 ──→ f2 ──→ artifact2 ──→ … ──→ 终态
              ▲                 ▲
         params/model v1   params/model v1
```

- **"再来一轮"不是 loop 的一次迭代，而是追加一条新分支**：
  同样的输入，换 `f2@v2`（新参数/新模型），产出新 artifact2′。
  旧链不删，新旧并存；查询层决定"当前认哪条链"。
- **"直到符合预期"从人在环的反复执行，变成声明式求值**：
  定义终态应满足的谓词，系统自己找缺口、跑处理器、再看谓词。

先例已经在库里：`transcripts` 对同一 `(part, source, language)` 不可变追加多个内容版本，
`publish-transcripts` 投影层决定哪个版本赢（`CONCEPTS.md` "transcript projection"）。
proofread 的一致率分级（≥0.85 一致 / 0.75–0.85 次要 / <0.75 待审）就是终态谓词的雏形。
**数据处理环节要做的就是把这个已验证的模式泛化到所有 artifact。**

## 5. 数据库：四个公理

"很牛逼的数据库"指的不是换一个重型引擎。
对本负载（单 writer、追加为主、批量读、字节本体在库外），
**SQLite + 不可变对象仓（文件系统）的组合再撑一两个数量级没有悬念**。
真正的规模瓶颈在字节本体，而字节永远不进数据库。

"很牛逼"指的是数据模型守住四条公理：

### 5.1 实体与事件分离

- **实体**（`videos` / `video_parts` / `audio_objects`）是可变的当前状态。
- **事件**（`ingestion_runs` / `acquisition_runs` / `acquisition_attempts` / 未来的 `processor_runs`）是不可变追加流。
  其中 `acquisition_runs` 是 `acquisition_attempts` 的父表，也是 ASR 运行已有的 run 级记录
  （`kind` 已含 `'asr'`，见 `storage/schema-transcripts.sql`）。
- 事件可以重放出实体；实体只是事件的缓存。

### 5.2 完整血缘

每次派生入库必须记录：

```
(input artifact ids, processor name, processor version, params, code/git 版本)
```

没有血缘的 artifact 不允许入库。
一年后对着一个旧 embedding 想知道"它到底是哪个模型、什么参数跑出来的"，血缘是唯一答案。

### 5.3 幂等键

```
(processor, version, input content hash, params hash)  唯一
```

"收集"就是对这个键求差集；重复跑不产生重复行。
（`asr-run-id-uniqueness` plan 补的就是这一类键。）

### 5.4 字节可逐出

字节本体可以删除（删文件、留行），因为**有血缘 + 有抓取记录，总能重新下载、重新派生**。

> "归档"不等于"字节永远在线"，而是"字节永远可重建"。

这一条把存储成本从无限变成有界，是"极度庞大"在成本维度的正解。
已有的 audio retention policy（`audio-retention-policy.md`）是这一公理的第一个实例。

### 5.5 这个模型叫什么

物化派生图（materialized derivation graph）：
**不可变、有血缘、可重放、可逐出**。这四个性质合起来就是"很牛逼的数据库"的完整定义。

## 6. 拓展方向在框架中的位置

三个已确认的方向，都不推翻三大环节的划分——这正是划分正确的证据。

### 6.1 评论

一个新的 source：实体表加 `comments` / `comment_events`，抓取环节多一个采集器，
下游处理和 ASR 走完全相同的派生管线。它检验的是 source 抽象够不够薄。

**边界挑战（已确认的设计决策）**：评论是活的、无限增长的，全量固化成本极高且边际价值低。
评论定义为**有界观察**（时间窗 / 条数封顶），承认有些数据不值得归档——
归档系统的智慧有一半在于"不归档什么"。

### 6.2 画面处理

在 audio 之外加一类字节本体：`video_objects` / `frame_objects`。
处理器是抽帧、场景切分、画面 OCR、以及 ASR 文本与画面 OCR 的对齐
（大量视频是板书/PPT 画面，OCR 与 ASR 文本互为校对，与 proofread 方法论同构）。
处理框架一行不用改，只是 `f` 的输入类型多一种。

### 6.3 视频之间的关系

三种关系，三种生命周期：

| 关系 | 来源 | 入库方式 |
|---|---|---|
| 声明的 | 合集、分 P、同 UP 主 | 抓取时固化 |
| 派生的 | 转录相似度、embedding 近邻 | 处理器算出，**必须标 processor 版本**（换算法关系就变） |
| 语料的 | 对某主题/问题的回答集合 | 查询层/策展层 |

## 7. 五条设计哲学

1. **观察不可变，派生可追溯。**
   抓取固化带时间戳的事实；一切处理是有血缘的派生。
2. **一切皆可重放。**
   除抓取外的任何环节可安全重算，重算不依赖外部世界。
3. **派生无删除，只有新的派生。**
   修正错误的方式是追加新版本并在查询层改指向，不是改写历史。
4. **身份与位置分离，字节可逐出。**
   数据库存身份与血缘，文件系统存字节；两者通过可重建性解耦。
5. **状态是计算的，不是存储的。**
   任何"当前状态"都能从事件流重新求出；存储的状态只是投影。

第五条是 `CONCEPTS.md` 既有 "evidence projection"（投影只描述、不回写状态）的泛化——
那条定义就是这个系统的设计哲学种子。

## 8. 务实边界（反过度设计）

派生图抽象是真实的架构开销。务实路径：

> **先收缩成一张 `processor_runs` 表 + 一个处理器注册表，服务音频这一件事；
> 画面和评论来了再泛化。**

目前只有一个处理器（ASR），N=1 时抽象必须薄。
通用图引擎等到第二个、第三个处理器真正出现时再长出来。
